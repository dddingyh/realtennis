# 手机体感手柄（Controller）说明

手机通过陀螺仪 / 加速度计当作球拍：**倾斜 = 走位，挥拍 = 击球**。挥拍会被识别为 平击 / 上旋 / 切削 / 挑高，并区分正手 / 反手。

## 1. 如何连接

1. 在游戏菜单里把“控制方式”选为 **手机体感**，画面会显示二维码和 6 位房间号。
2. 手机扫码（或打开 `…/controller.html`，手动输入房间号）。
3. 点 **开始** → 允许“动作与方向”权限（iOS 会弹窗）→ 选惯用手 → 握拍并校准中立位 → （可选）挥拍校准 → 进入比赛。
4. 手机屏幕顶部显示“已连接”和延迟（ms）；游戏画面也会显示连接状态。

连接方式：默认走 PeerJS（WebRTC DataChannel，信令走公共服务器 `0.peerjs.com`，之后数据点对点传输）。开发测试时用 `?local=1`，游戏页与手柄页在**同一浏览器**里通过 BroadcastChannel 互通，不需要网络。

### 桌面调试（无手机）
`controller.html?room=XXXXXX&sim=1`（本机测试再加 `&local=1`）会出现“传感器模拟器”：
鼠标拖动小方块 = 倾斜；`1–4` 选择击球类型（平击/上旋/切削/挑高），`F`/`B` 选正手/反手，空格 = 挥拍；“时机 早/中/晚”改变击球时拍面朝向（方向），“动作 标准/抖动/急停”改变动作质量；可勾选“反面持握”“走路抖动”。模拟器生成的是物理一致的 IMU 数据流（刚体绕肩关节摆动，含向心/切向加速度、重力、噪声），**走与真机完全相同的识别流程**。

## 2. 握法（约定）

- 像握**网球拍柄**一样握住手机的**下端**，手机**顶端 = 拍头**，**屏幕所在平面 = 拍面**。
- 中立（准备）姿势：拍头朝正前方并略微抬高（约 30°），拍面竖直。手臂自然弯曲。
- 推荐：右手持拍时屏幕作为**正手击球面**（反手时手机背面朝前）。但识别全部基于**重力参照的世界坐标量**，所以屏幕朝哪一面、手机绕竖直轴转到哪个朝向都不影响结果（测试覆盖了两种持握方向）。
- 挥拍要像**地面击球**那样绕身体水平挥（绕竖直轴转动为主）。像“甩锤子”一样上下抡（绕水平轴）会让正反手判断失准。
- 安全：请握紧或戴腕带，手机很滑。

### 走位（倾斜）
以校准的中立位为零点（低通滤波后的重力方向）：

| 动作 | 效果 |
|---|---|
| 拍头压低（向前点） | 向球网前进 |
| 拍头抬高 | 后退 |
| 整支球拍以握把为轴向右“倒” | 向右移动 |
| 向左倒 | 向左移动 |

死区约 5°，约 28° 满量程；挥拍期间及挥拍后 0.3 秒内倾斜输出**冻结**（避免挥拍动作被当成走位）。游戏端默认 `autoMove: 'assist'`，倾斜只是“引导”，不需要精确控制。

## 3. 挥拍识别

检测：陀螺仪合角速度 |ω| 超过 200 °/s 开窗，峰值须达到 380 °/s；**击球时刻 = |ω| 峰值**；峰值后约 70 ms 输出结果（需要一点随挥特征），之后 450 ms 不应期。力度 = 峰值角速度映射（300 °/s → 0.2，1200 °/s → 1.0）。

内部先用陀螺仪积分 + 重力校正维护完整姿态，得到世界坐标系下的量。特征（均为世界坐标、与持握面无关）：

| 特征 | 定义 | 含义 |
|---|---|---|
| `yaw` | 击球时刻角速度在“竖直向上”轴上的分量（°/s，带符号） | **正/反手**：右手 yaw>0（逆时针，从右后向左前挥）= 正手；左手相反 |
| `rise` | 窗口内线加速度（去重力）积分得到的手部速度，在击球时刻的仰角（°） | 由低向高刷 = 正值；由高向低切 = 负值 |
| `face` | 击球面法线的仰角（°）。击球面 = 与手部水平速度同向的那一面 | 正 = 拍面开放（朝上），负 = 拍面关闭（朝下） |
| `roll` | 拍面仰角的变化率（°/s）= 绕拍杆长轴的翻转速度 | 负 = 正在关拍（上旋的翻腕），正 = 在开拍 |
| `dur` | 从 25% 峰值到峰值的时间（ms） | 加速段长短 |
| `peak` | 峰值 \|ω\|（°/s） | 力度 |

击球类型（默认原型，`gesture.js` 里的 `PROTO`；以 `rise`/`face` 为主，`roll`/`dur`/`peak` 权重小）：

| 类型 | 样子 | rise | face |
|---|---|---|---|
| 平击 | 平稳水平挥，拍面竖直 | ≈ 0° | ≈ 0° |
| 上旋 | 由低向高刷，拍面略关闭，翻腕 | ≈ +15° 以上 | 负（≈ −10°） |
| 切削 | 由高向低切，拍面略开放 | ≈ −12° | 正（≈ +20°） |
| 挑高 | 从下往上大幅“捞”，较慢，拍面朝上 | ≈ +25° 以上 | 大正（≈ +35°） |

`conf`（0–1）= 最近两个类型的距离裕度 × 正反手可信度（\|yaw\|/\|ω\|）。

### 挥拍校准（强烈建议）
默认原型来自物理推理 + 合成数据，**不同人的动作差异很大**。校准向导让每种击球挥 3 次，保存到 `localStorage`，之后改用“按你自己的特征均值 + 池化标准差”的最近中心分类（z 归一化）。校准没做完的类型回退到默认原型。设置里可随时重做 / 清除。

### 触屏兜底
- 比赛页的 平击 / 上旋 / 切削 / 挑高：**按住**可强制下一次挥拍的类型（主机收到 `btn shotOverride`，并且手机端也会改写 `swing.shot`）。
- 设置里打开“触屏模式”：点按钮 = 直接击球（正反手由游戏自动选择）。
- “发球”按钮 = 发球；“暂停/继续”。

## 3b. 怎么打：力度、方向、旋转、弧度与动作质量

除了离散的击球类型，每次挥拍还会发送连续的“模拟量”（见 `DESIGN.md` §6.2）。同一类击球里，轻上旋和重上旋、慢挑高和快挑高都会打出不同的球。

| 量 | 范围 | 你怎么控制 |
|---|---|---|
| **力度** `power` / `speedDps` | 0–1 / °/s | 挥得越快越重。默认 300 °/s → 0.2，1200 °/s → 1.0；做过挥拍校准后，按**你自己**的平击 / 上旋平均速度归一（你的平常速度 ≈ 0.75），力气小的人也能打出重球。 |
| **方向** `aimX` | −1（左）… +1（右） | 由**击球瞬间拍面朝向**决定（相对于这次挥拍开始前准备姿势时的正前方）。拍面偏 30° 约等于打满。 |
| **旋转** `spin` | −1 切削 … 0 平 … +1 上旋 | 由三件事共同决定：挥拍路径的仰角（由下往上 → 上旋）、拍面仰角（关闭/向下 → 上旋，打开/朝上 → 下旋）、击球时手腕绕拍柄的翻转（翻腕关拍 → 上旋）。 |
| **弧度** `lift` | 0 平直 … 1 很陡 | 只看挥拍路径的上扬程度：越是从下往上捞，球越高。高弧度 + 慢速 ≈ 挑高。 |
| **动作质量** `exec` | 0–1 | 见下。手机上显示为 **完美 / 好 / 一般 / 差**，并提示主要问题。 |

### 方向约定（重要）
- 以**这次挥拍开始前的准备姿势**里拍头所指方向为“正前方”（只在 ~1 秒内用陀螺仪积分，漂移可以忽略）。
- `aimX` 是拍面在水平面里的朝向：负 = 偏向你的**左边**，正 = 偏向你的**右边**。这是绝对的左右方向，不随正反手翻转。
- 因为击球点越靠前，拍面转得越多：
  - **右手正手**：击球早（球在身体前方更远处）→ 拍面已转向左 → `aimX < 0` → **斜线**；击球晚 → 拍面朝右 → **直线**。
  - **右手反手**：击球早 → 拍面朝右 → `aimX > 0` → 斜线。
  - **左手**完全镜像：左手正手早 → 朝右（斜线），左手反手早 → 朝左（斜线）。
- 手机上的箭头直接画这个方向，并标出“斜线 / 直线 · 偏左 / 偏右”。
- 游戏会把 `aimX` 与真实的击球时机结合起来决定落点。
- 做过挥拍校准时，会减去你在校准挥拍（请都朝正前方打）里习惯性的拍面偏角（正手、反手各算一次）。

### 怎么打出各种球
- **平击（重炮）**：水平、快速、干脆地挥，拍面竖直正对目标 → `spin≈0`、`lift≈0`、力度高。
- **上旋**：从膝盖高度由下往上“刷”，拍面略向下压，击球后手腕顺势翻过。刷得越陡、翻腕越明显，旋转越强（轻上旋 ≈ 0.4–0.6，重上旋 ≈ 0.9）。
- **切削**：从肩高往下、往前切，拍面朝上打开，动作放松 → `spin < 0`。
- **挑高**：从低处往上大幅度“捞”，拍面朝上，速度放慢 → `lift` 高。
- **打斜线**：击球点靠前、拍面提早转向场内；**打直线**：让拍面在身体侧面多停一会儿、晚一点“出手”。

### 什么是“好”的挥拍（`exec`）
`exec` 只看动作本身（游戏还会再结合击球时机和站位）：

| 子项 | 怎么测 | 扣分的情况 |
|---|---|---|
| 拍面稳定 | 击球前后 ±60 ms 内拍面仰角相对一条直线的抖动（RMS） | 拍面晃动（>~1°开始扣分，~3.5° 扣满） |
| 加速平顺 | \|ω\|(t) 从 25% 峰值到峰后 70 ms，与局部二次拟合的残差 + 加速段中途“掉速”的总量 | 一顿一顿、忽快忽慢 |
| 随挥完整 | 峰后 70 ms 的平均角速度 ÷ 峰前 70 ms 的平均角速度 | 打到就急停（比值 < ~0.9 开始扣分，0.55 扣满） |
| 节奏 | 加速段（25% 峰值 → 峰值）的时长 | < 70 ms（只甩手腕）或 > 320 ms（推、拖） |
| 拍面对准 | 拍面水平朝向与手的运动方向夹角 | > 20° |

完美的挥拍：从准备姿势平稳加速，击球时拍面稳定，击球后**继续挥完**（收拍到对侧肩膀）。

## 4. 通信协议（v1）
见 `docs/DESIGN.md` §4.4。补充：
- 主机用 ping/pong 估计 RTT 与时钟偏差（取最近样本里 RTT 最小的几个），`swing` 到达时计算 `ageMs = hostNow − (phoneTs − offset)` 并附加在消息上（0–400 ms）。`ageMs` 包含检测延迟（约 70–150 ms）+ 网络延迟。
- 倾斜走单独的 `reliable:false`（无序）通道，丢失回退到可靠通道。注意 PeerJS 1.5.4 的 `reliable:false` 只是“无序”，不是“不重传”。
- 自动重连：手机端指数退避；主机端监控信令断开并重连；6 秒无消息显示“无响应”。
- `RemoteInput`（`src/input/remote.js`）：`timingOffsetMs` 可由游戏设置面板暴露，用于补偿设备固有延迟；手机端设置里还有“挥拍时间校正”（±120 ms）。

## 5. 故障排查

| 现象 | 处理 |
|---|---|
| 页面提示需要 HTTPS | 传感器只在安全上下文开放。请通过 GitHub Pages（https）打开；局域网 `http://192.168.x.x` 不行（iOS/Android 都不行）。`http://localhost` 可以（仅限本机）。 |
| iOS 点“开始”没有弹窗 / 提示未授权 | 设置 → Safari → “动作与方向访问”打开；或清除该网站数据后重新扫码。权限请求必须由点击触发，不要刷新后直接进入。 |
| Android 没数据 | Chrome 地址栏左侧 → 网站设置 → “动作传感器”允许；省电模式可能降低采样率。 |
| 连不上 | 先看两端显示的状态（见下方“连接状态说明”）定位卡在哪一步。 |
| 倾斜方向与预期相反 | 设置 → “倾斜方向反了”切换（部分 iOS 机型 `accelerationIncludingGravity` 符号相反，默认已对 iOS 取反）；然后重新校准中立位。 |
| 击球总是偏晚 / 偏早 | 设置里调“挥拍时间校正”，或在游戏里调 `timingOffsetMs`。 |
| 误触发挥拍 | 走路时手机剧烈晃动可能误判；挥拍阈值可在 `gesture.js` 的 `DEFAULTS` 调整（`minPeakDps`）。 |
| 正反手判反 | 左右手选反了，或握拍时挥拍平面不是水平的。 |
| iOS 没有震动 | iOS Safari 不支持 `navigator.vibrate`，静默降级。 |

### 连接状态说明

连接分三步，两端都会显示当前卡在哪一步：

1. **信令**：电脑和手机分别连上 PeerJS 公共服务器 `0.peerjs.com`。电脑端一直显示“正在连接信令服务器…” → 电脑访问不了该服务器（网络或代理问题）。
2. **找主机**：手机通过房间号找到电脑。手机显示“找不到主机 / 主机无应答” → 房间号不一致，或电脑端游戏页已关闭或刷新（刷新后房间号会变，需要重新扫码）。
3. **点对点（WebRTC/ICE）**：电脑端显示“发现手机，点对点连接：正在打洞”，手机端显示“点对点连接：…”。如果一直停在这里或显示“失败”，说明两台设备之间打不通：
   - 确认手机和电脑连的是**同一个 Wi‑Fi**（不要一个用 5G 蜂窝网络、一个用 Wi‑Fi）。
   - 很多路由器会开启 **AP 隔离 / 访客网络隔离**（同一 Wi‑Fi 下设备之间互相看不见），访客网络尤其常见。可以换主网络，或让电脑连手机热点。
   - 中国大陆访问不了 Google 的 STUN，所以现在优先使用国内可用的 STUN（`stun.miwifi.com`、`stun.chat.bilibili.com`），之后才是 Cloudflare、Google，最后用 PeerJS 公共 TURN 中转兜底（中转延迟会明显变高）。
   - 电脑上的 VPN 或代理软件可能干扰 WebRTC，可以暂时关掉再试。
   - 部分 App 内置浏览器（如微信）对 WebRTC 支持不完整，请在系统浏览器（Safari / Chrome）中打开扫码得到的链接。

## 6. 诚实的局限

- **识别准确率只在合成数据上验证过**（见下）。合成数据由我们自己写的刚体模型生成，参数分布也是我们假设的；真实用户、真实手机、真实握法会差很多。默认判定仅是起点，请做挥拍校准。
- 打出的击球类型靠“手部路径仰角 + 拍面仰角”区分，真实挥拍时这两者与“握拍方式 / 手腕动作”强耦合；手机没有拍面“击球”的物理反馈。
- 线加速度积分只用于窗口内的速度方向，存在漂移，也受重力估计误差影响；手机 IMU 采样率不稳定（iOS 常 60 Hz、Android 视机型）会降低高速挥拍下的姿态积分精度。
- 角速度单位：W3C 为 °/s；极老的 Android 为 rad/s，识别器按“强烈运动但读数很小”自动判定，第一次挥拍可能被误判。
- 本容器无法访问外网，**PeerJS 公共信令 / WebRTC 路径没有端到端测试过**；仅在本机用 BroadcastChannel 测试了同一份协议与逻辑。
- 方向 / 旋转 / 弧度 / 动作质量的阈值同样只在合成数据上检验过单调性和符号；它们与真实球拍击球的对应关系（比如多少度的拍面偏转算“打满”）是我们设定的，需要真人试玩来调整。`exec` 对真实手抖、握持松动的敏感度未知。
- 很快的引拍（引拍角速度接近正式挥拍）可能被当成一次挥拍，从而让紧跟的正式挥拍落在不应期里。
- 发球目前不做“抛球 + 过顶挥拍”识别：用“发球”按钮或在发球阶段的一次挥拍触发。
- 没有在真机上测过：iOS 权限弹窗流程、Wake Lock、震动、实际采样率与符号约定。

## 7. 测试

```
node tests/gesture.test.mjs     # 合成轨迹：混淆矩阵、走路抖动、倾斜、校准、rad/s、模拟量单调性
node tests/net.test.mjs         # 协议 / 时钟同步 / BroadcastChannel / RemoteInput
node tests/e2e.mjs [截图目录]    # Playwright：游戏端 + 手机端(sim) 全流程
```

合成数据结果（`node tests/gesture.test.mjs`，R/L × 屏幕朝前/朝后 × 60/100 Hz × 4 类型 × 2 边 × 10 次 = 640 次）：
类型与正反手均 100%（建模分布内），击球时刻误差中位数约 1 ms；“马虎用户 + 3 倍传感器噪声”压力测试：类型 ≈ 89%，正反手 ≈ 98%。

模拟量（每个旋钮单独扫描，R/L × 正反手 × 60/100 Hz，Spearman 相关）：挥速→力度 0.95；击球时机（拍面朝向真值）→`aimX` 0.98（方向误差中位数约 3°，p90 约 8°）；路径仰角→`lift` 0.95、→`spin` 0.98；拍面仰角→`spin` −0.98；手腕翻转→`spin` −0.98；抖动→`exec` −0.88；收拍过早→`exec` −0.94。干净挥拍 `exec` 中位数 1.0，严重抖动约 0.35，完全急停约 0.42。**这只说明算法在这套模型里自洽，不代表真机表现。**
